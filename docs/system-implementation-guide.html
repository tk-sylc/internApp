INTRODUCTION

このガイドでできるようになること

完成済みコードの暗記ではなく、入力欄を追加したときに、保存先・通信処理・管理画面・テストまで自分で変更できることを目標にします。

完成形：ログイン画面から申請種別を選び、申請者情報と申請内容を入力して送信すると、Djangoが検証してSQLiteへ保存します。保存結果はDjango管理画面で検索・確認できます。

全体像

React
画面・入力・送信
→
Django
受付・検証・保存
→
SQLite
申請データを保持

ブラウザはSQLiteを直接操作しません。ReactがJSONをDjangoへ送り、DjangoのORMがSQLを組み立ててSQLiteを操作します。この役割分担がシステムの中心です。

外部記憶装置貸出氏名、機器名、容量、場所、貸し出し日ExternalStorageLoanApplication
LAN機器貸出機器種別、機器名、利用開始日、返却予定日、利用場所LanEquipmentLoanApplication

全申請に共通して、申請者氏名・所属部署・社員番号も手動入力します。

CHAPTER 2

Reactで申請画面を組み立てる

src/App.jsx は、画面遷移、フォーム定義、入力値の収集、Djangoへの送信を担当します。

1. 項目をデータとして定義する

申請ごとにフォームを複製せず、REQUEST_TYPES に「項目の設計図」を置きます。共通の描画処理がこの配列を読み、inputやselectを生成します。

const REQUEST_TYPES = {
  pc: {
    title: 'PC貸出',
    fields: [
      { name: 'applicantName', label: '氏名', type: 'text', required: true },
      { name: 'managementNumber', label: '管理番号', type: 'text', required: true },
      { name: 'startDate', label: '使用開始日', type: 'date', required: true },
      { name: 'location', label: '利用場所', type: 'text', required: true },
    ],
  },
  // memory, lan, phone も同じ形式で定義
}

name は通信で使うキーです。後述するDjangoの対応表と一文字単位で一致させます。

2. 申請者情報を共通化する

const APPLICANT_FIELDS = [
  { name: 'requesterName', label: '氏名', type: 'text', required: true },
  { name: 'department', label: '所属部署', type: 'text', required: true },
  { name: 'employeeNumber', label: '社員番号', type: 'text', required: true },
]

FormField が項目定義を受け取り、type に応じてinputまたはselectを返します。新しい項目は原則として配列への1件追加で表示できます。

CHAPTER 3

Djangoでデータベースを設計する

backend/applications/models.py のモデルは、Pythonで書くデータベースの設計図です。DjangoがこれをSQLiteのテーブルに変換します。

共通項目を抽象モデルにする

class BaseApplication(models.Model):
    requester_name = models.CharField('申請者氏名', max_length=100)
    department = models.CharField('所属部署', max_length=100)
    employee_number = models.CharField('社員番号', max_length=30)
    created_at = models.DateTimeField('作成日時', auto_now_add=True)
    updated_at = models.DateTimeField('更新日時', auto_now=True)

    class Meta:
        abstract = True

abstract = True により、BaseApplication専用テーブルは作られません。各申請モデルに共通列を引き継ぐための設計部品になります。

申請種別ごとのモデルを作る

class PcLoanApplication(BaseApplication):
    applicant_name = models.CharField('氏名', max_length=100)
    management_number = models.CharField('管理番号', max_length=50)
    start_date = models.DateField('使用開始日')
    location = models.CharField('利用場所', max_length=200)

class ExternalStorageLoanApplication(BaseApplication):
    applicant_name = models.CharField('氏名', max_length=100)
    device_name = models.CharField('機器名', max_length=100)
    capacity = models.CharField('容量', max_length=50)
    location = models.CharField('場所', max_length=200)
    loan_date = models.DateField('貸し出し日')
DjangoフィールドSQLiteでの意味用途
CharField文字列列氏名、番号、場所など
DateField日付列使用開始日、貸し出し日など
DateTimeField日時列作成・更新日時
TextChoices許容値を限定LAN機器種別、容量、SIM有無

モデル自身に業務ルールを書く

def clean(self):
    super().clean()
    if self.start_date and self.return_date \
            and self.return_date < self.start_date:
        raise ValidationError({
            'return_date': '返却予定日は利用開始日以降にしてください。'
        })

この例はLAN機器の返却予定日が開始日より前になるのを防ぎます。画面側だけでなくモデル側にも書くことで、管理画面や別処理から保存するときも同じルールが働きます。

CHAPTER 4

マイグレーションで設計をDBへ反映する

モデルを書いただけではSQLiteのテーブルは変わりません。設計変更を履歴にし、その履歴をDBへ適用するのがマイグレーションです。

models.py
Pythonの設計
→
migration
変更手順
→
db.sqlite3
実際の表
cd backend
.\.venv\Scripts\python.exe manage.py makemigrations
.\.venv\Scripts\python.exe manage.py migrate
  • makemigrations：モデルとの差分を読み、migrationsフォルダに変更手順を作る。
  • migrate：未適用の変更手順をSQLiteへ実行する。
# 適用状況
.\.venv\Scripts\python.exe manage.py showmigrations

# モデルとmigrationに差分がないか
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
db.sqlite3だけを直接編集しない：チームで同じ構造を再現するには、モデルとmigrationをGitで共有します。通常、個人の実データを含むdb.sqlite3は共有対象から外します。

SQLiteとSQLの位置づけ

SQLはデータの追加・検索・更新・削除を指示する言語です。SQLiteはSQLを理解し、1個のファイルにデータを保存するデータベースソフトです。このシステムではDjango ORMがSQLを自動生成するため、通常はSQLを手書きしません。

CHAPTER 5

URLと保存処理を実装する

「URLを登録する」とは、届いたURLと実行するPython関数を対応付けることです。

URLを二段階で接続する

# backend/config/urls.py
urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/', include('applications.urls')),
]

# backend/applications/urls.py
urlpatterns = [
    path('csrf/', csrf_token, name='csrf-token'),
    path('applications/', create_application, name='create-application'),
]

結果として /api/csrf/ はcsrf_token関数へ、/api/applications/ はcreate_application関数へ到達します。末尾のスラッシュもReact側と合わせます。

React名とDjango名を対応付ける

APPLICATION_SETTINGS = {
    'pc': {
        'model': PcLoanApplication,
        'fields': {
            'applicantName': 'applicant_name',
            'managementNumber': 'management_number',
            'startDate': 'start_date',
            'location': 'location',
        },
    },
    # memory, lan, phone も定義
}

JavaScriptではcamelCase、Pythonではsnake_caseが一般的です。この辞書は表記を変換し、申請種別ごとに保存モデルを選びます。

JSONを検証して保存する

@require_POST
def create_application(request):
    payload = json.loads(request.body or '{}')
    request_type = payload.get('requestType')
    settings = APPLICATION_SETTINGS.get(request_type)

    model_values = {
        'requester_name': payload.get('requesterName'),
        'department': payload.get('department'),
        'employee_number': payload.get('employeeNumber'),
    }
    for frontend_name, model_name in settings['fields'].items():
        model_values[model_name] = payload.get(frontend_name)

    application = settings['model'](**model_values)
    application.full_clean()
    with transaction.atomic():
        application.save()

    return JsonResponse({'id': application.pk}, status=201)
  1. JSONをPythonの辞書へ変換する。
  2. requestTypeからモデルと項目対応を選ぶ。
  3. full_clean()で必須、長さ、日付、選択肢、独自ルールを検証する。
  4. transaction.atomic()内で保存し、途中失敗時の中途半端な更新を防ぐ。
  5. 成功時はHTTP 201とIDを返す。入力不正は400を返す。
CHAPTER 6

CSRFで不正送信を防ぐ

CSRFは、利用者がログイン済みのサイトに対して、別サイトから意図しない操作を送らせる攻撃です。DjangoはPOSTに秘密の照合値を要求して防ぎます。

正常な送信の順序

  1. Reactが GET /api/csrf/ を呼ぶ。
  2. Djangoがブラウザへcsrftoken Cookieを発行する。
  3. ReactがCookieを読み、POSTのX-CSRFTokenヘッダーへ入れる。
  4. DjangoがCookieとヘッダーを照合し、一致すれば保存処理へ進む。
# views.py
@require_GET
@ensure_csrf_cookie
def csrf_token(request):
    return JsonResponse({'message': 'CSRF Cookieを発行しました。'})

# settings.py
CSRF_TRUSTED_ORIGINS = [
    'http://localhost:5173',
    'http://127.0.0.1:5173',
]
信頼済みOriginとは：「このURLで動くフロントエンドからの安全なPOSTを受け入れる」という許可リストです。ホスト名、ポート、http/httpsのどれかが違えば別Originです。

React側のトークン取得

async function getCsrfToken() {
  const existingToken = getCookie('csrftoken')
  if (existingToken) return existingToken

  const response = await fetch('/api/csrf/', {
    credentials: 'same-origin',
  })
  if (!response.ok) {
    throw new Error('セキュリティ情報を取得できませんでした。')
  }
  return getCookie('csrftoken')
}

csrf_exempt で保護を外す方法は採用していません。原因を直してCSRF検証を通す方が、安全な設計を維持できます。

CHAPTER 8

submitRequestを非同期処理にする

非同期処理とは、通信完了を待ちながらブラウザ全体を再読み込みせず、成功・失敗に応じて画面だけを更新する処理です。

const submitRequest = async (event) => {
  event.preventDefault()
  setIsSubmitting(true)
  setSubmitError('')

  try {
    const formValues = Object.fromEntries(new FormData(event.currentTarget))
    const csrfToken = await getCsrfToken()
    const response = await fetch('/api/applications/', {
      method: 'POST',
      credentials: 'same-origin',
      headers: {
        'Content-Type': 'application/json',
        'X-CSRFToken': csrfToken,
      },
      body: JSON.stringify({
        requestType: selectedType,
        ...formValues,
      }),
    })

    const data = await response.json()
    if (!response.ok) throw new Error(getSubmissionError(data))
    setSubmissionId(data.id)
    setIsComplete(true)
  } catch (error) {
    setSubmitError(error.message)
  } finally {
    setIsSubmitting(false)
  }
}
コード役割
preventDefault()フォーム標準のページ再読み込みを止める
FormDataname属性が付いた入力値をまとめて収集する
await fetch(...)HTTP応答が返るまで、この関数内の次処理を待つ
response.okHTTP 200番台かを判定する
try / catch通信・JSON・サーバーエラーを画面表示へ変換する
finally成功・失敗の両方で通信中状態を解除する

ボタンを押しただけでは完了扱いにせず、Djangoが保存して201を返した後だけ完了画面へ進めるのが重要です。

CHAPTER 9

Django管理画面を有効にする

管理画面はDjango標準機能です。URL、標準アプリ、モデル登録の3点がつながって動きます。

# config/urls.py
path('admin/', admin.site.urls)

# applications/admin.py
@admin.register(PcLoanApplication)
class PcLoanApplicationAdmin(BaseApplicationAdmin):
    list_display = (
        'id', 'management_number', 'applicant_name',
        'department', 'start_date', 'location', 'created_at',
    )
    search_fields = ('requester_name', 'management_number', 'location')
    list_filter = ('start_date', 'department')

@admin.register がモデルを管理画面へ登録します。list_displayは一覧列、search_fieldsは検索対象、list_filterは絞り込み項目です。

管理者を作成して確認する

cd backend

.\.venv\Scripts\python.exe manage.py runserver

パスワード検証もDjango標準機能です。AUTH_PASSWORD_VALIDATORS により、ユーザー名との類似、8文字未満、よくある文字列、数字だけなどが検査されます。平文パスワードはDBへ保存されません。

症状主な原因確認・対処
sites-vite-pluginを解決できないnode_modulesに依存パッケージがないプロジェクト直下で npm install。package.jsonも確認。

切り分けの順番

  1. Djangoのターミナルに例外やHTTPステータスが出ているか。
  2. ブラウザのNetworkで、どのリクエストが何番で失敗したか。
  3. Response本文にDjangoの検証理由があるか。
  4. Request Payloadのキー名と値が期待どおりか。
  5. モデル、対応表、Reactのname属性が一致しているか。

画面のメッセージだけで推測せず、HTTPステータスと送受信内容を見れば問題の層を絞れます。

CHAPTER 13

新しい申請項目を追加する練習

例としてPC貸出に「返却予定日」を追加する場合、次の順序で変更します。

  1. 画面：REQUEST_TYPES.pc.fields にreturnDateを追加。
  2. モデル：PcLoanApplication にreturn_dateを追加。
  3. 対応表：'returnDate': 'return_date' を追加。
  4. DB：makemigrationsとmigrateを実行。
  5. 管理画面：list_displayやlist_filterに追加。
  6. テスト：正常値の保存と不正値の拒否を追加。
  7. 確認：Djangoテスト、lint、build、画面送信、管理画面を順に確認。
変更の一本線：inputのname → 送信JSONのキー → APPLICATION_SETTINGS → モデルのフィールド → SQLiteの列。値が消えたときは、この線を左からたどります。

  • 新しい入力欄を追加し、対応するモデル列を作れる。

  • 管理画面と自動テストで保存を確認できる。

用語集と本番化の注意

用語このシステムでの意味
React状態に応じてログイン、一覧、入力、完了画面を描画するライブラリ。
ViteReactの開発サーバーとビルドを担当し、開発中は/apiをDjangoへ転送。
DjangoURL受付、CSRF、入力検証、ORM、管理画面、認証基盤を提供。
モデル保存項目の型、長さ、選択肢、ルールを表すPythonクラス。
ORMPythonオブジェクト操作をSQLへ変換する仕組み。
SQLitebackend/db.sqlite3という1ファイルで動く開発向けDB。
APIReactとDjangoがJSONでデータを受け渡す窓口。
CSRF第三者サイトからの意図しないPOSTを防ぐ仕組み。
migrationモデル変更をDB構造へ再現可能に適用する履歴。

本番環境へ進む前に

  • DEBUG = False、安全なSECRET_KEY、適切なALLOWED_HOSTSを設定する。
  • HTTPSを必須にし、CSRF/Cookieの本番設定を見直す。
  • 画面だけのログインをDjango認証へ置き換え、権限と操作履歴を設計する。
  • 個人情報の保存期間、閲覧権限、バックアップ、削除手順を定める。
  • 規模に応じてPostgreSQLなどのサーバー型DBを検討する。
  • Djangoの開発サーバーではなく、本番用構成で配信する。
この実装は学習・開発用の土台です。特に現在のログイン画面は本人確認をしていないため、そのまま社内本番システムとして公開しないでください。

最後に：実装を理解する最短ルート

まずPC貸出だけを対象に、入力 → JSON → view → model → SQLite → adminの一本を自分で再現してください。一本が理解できれば、他の申請は同じ構造の横展開です。機能を追加するたびに正常系と異常系のテストも増やすと、壊れにくいシステムになります。
